### "55 failed"判为环境假象的证据链

1. **收集数恒等**：两轮全量均收集 396 例（394+2），与卡面 55+339+2=396 完全一致 →
   用例集没变，变的只是当时的运行环境。
2. **`.pytest_cache/v/cache/lastfailed` 无 55 条记录**：仅 5 条**更早期**的陈旧条目
   （`test_wear_conflicts_with_new`、`test_luggage_text_40_over_20...`、3 条 v10 金标用例），
   这些节点 ID 在现行代码中已改名/不存在，属跨时代残留 → 55-failed 那轮要么没写这份缓存
   （不同 rootdir/解释器启动），要么其后跑过全绿覆盖。
3. **conftest 注释自证前科**：`_initial_cleanup` 已含上一轮对"随机 401 / StaleDataError"的
   机制修复（先删库文件再 drop_all，engine.dispose 防连接池陈旧），并明确记载该症状系
   "残留 SQLite 文件 + 连接池陈旧连接"；`tests/test_zz_diag.py` 即当时排查遗留的临时诊断
   文件（文件头自述"临时诊断……验证完毕即删"，可作时间线物证）。
4. **最可能触发场景（推断，置信中）**：55-failed 测量与"被中断的上一派遣"发生了并发——
   两个 pytest 进程共用 `tests/_mvp_qa.db`，一方 `os.remove` 删库正好落在另一方运行中，
   即成片 401 / StaleDataError（与 conftest 记载的症状完全吻合）。本卡资源纪律
   "绝不并发跑多份 pytest"正是针对此坑。证据不足处如实标注：无法百分百回溯当时进程表。
