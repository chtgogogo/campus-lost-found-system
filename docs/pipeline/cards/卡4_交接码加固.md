# 卡 #4（失物招领）：交接码加固——role 服务端推导 + 错 5 次锁定 + 恒时比较（安检 L1-9）
- 背景（安检 L1 第 9 项阻断）：①verify 的 role 由请求体自报（match.py:474 `role=body.role`），服务端按 role 分支比对与刷状态——失主可自报 role="finder" 并输入自己屏幕上的 lost_code，冒充拾得者完成验证，单方刷满双方 verified 把匹配打成 COMPLETED；②4 位码 1 万组合+无尝试次数限制可穷举；③码比较用普通 `!=` 非恒时比较（同文件邀请码用了 compare_digest，双标准）；④比对在前、过期检查在后，会泄露"码对但过期"信号。
- 涉及文件：`app/routers/match.py`（handover_verify 路由）、`app/services/handover_service.py`（verify 逻辑）、`app/models/`（HandoverCode 加字段）、**新迁移文件**（Alembic 0009，接续现有 0001-0008）、相关测试文件、`docs/pipeline/安检报告.md`（回填 L1-9）、`CHANGELOG.md`。
- 实现要点：
  1. **role 服务端推导（核心）**：路由层已有身份校验（user.id ∈ {lost.publisher_id, found.finder_id}），在此基础上推导 `real_role = "lost" if int(user.id)==int(lost.publisher_id) else "finder"`；`body.role` 仅作对账——`body.role != real_role` 时抛 422（"角色与身份不符"），传给 service 的一律是推导出的 real_role。service.verify 签名不动（最小改动），但语义变为"必然是真实角色"；
  2. **错 5 次锁定**：HandoverCode 模型加 `attempts INTEGER NOT NULL DEFAULT 0` 列 + Alembic 迁移（手写 upgrade/downgrade，参考 0008 风格）；verify 中码错误时 `attempts += 1`，`attempts >= 5` → 该 HandoverCode 行 status 置失效（用现有状态，不新增枚举值），后续 verify 返回"验证码已锁定，请双方重新生成交接码"类明确错误；重新 generate 会创建新 seq 行，天然解锁（generate 仅双方可调，语义安全）；验证入口先查行是否已失效；
  3. **恒时比较+顺序**：码比对改 `hmac.compare_digest`（注意 target_code 可能为 None 的前置判断）；调整顺序为"先查过期、再比对码"，错误信息不区分"码对但过期"；
  4. **测试更新（正向修正非凑绿）**：新增用例——"失主传 role=finder 必须被拒（422）""连续错 5 次后正确码也被锁定""role 与身份一致的正向流程不受影响"；既有依赖自报 role 行为的用例改为按新语义修正；
  5. 回填安检报告 L1-9 为已修复；CHANGELOG 接续最新版本。
- 验收（必须实际执行并贴完整输出）：
  1. **攻击路径复现失败**：构造失主身份 token 调 verify 传 `role="finder"` + 失主自己屏幕上的码 → 必须 422（贴 curl/pytest 输出）；
  2. 锁定验证：同 match 连续 5 次错码 → 第 6 次即使码正确也报锁定（贴输出）；
  3. 正向双验证流程回归：失主/拾得者各自正确验证 → both_verified、COMPLETED 全链不变（贴输出）；
  4. `pytest` 全量 0 failed（**串行单进程**，贴末尾统计+EXIT）；迁移 up/down 可执行（`alembic upgrade head` 后 `downgrade -1` 再 `upgrade head`，贴输出）；
  5. py_compile 通过；git status 变更仅限清单。
