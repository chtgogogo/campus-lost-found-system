## L1-9 交接码安全 —— ✅ 已修复（卡#4 回填，2026-09-23）

**原状（四项指控均属实）**：
① verify 的 role 由请求体自报（`match.py` `role=body.role`），服务端按 role 分支比对与刷状态——失主可自报 `role="finder"` 并输入自己屏幕上的 lost_code，冒充拾得者完成验证，单方刷满双方 verified 把匹配打成 COMPLETED；
② 4 位码 1 万组合 + 无尝试次数限制，可在线穷举；
③ 码比较用普通 `!=` 非恒时比较（同文件邀请码用了 `compare_digest`，双标准）；
④ 比对在前、过期检查在后，会泄露"码对但过期"信号。

**修复**：
- **role 服务端推导**：路由层在既有身份校验（`user.id ∈ {lost.publisher_id, found.finder_id}`）基础上推导 `real_role`，`body.role` 仅对账——不一致一律 422（"角色与身份不符"）；传给 service 的一律是推导出的真实角色（service.verify 签名不动，语义变为"必然是真实角色"）；
- **错 5 次锁定**：`handover_code` 新增 `attempts` 列（迁移 `0009_handover_attempts`，server_default 0）；错码 +1，达 5 次（`HANDOVER_MAX_ATTEMPTS`）整行 status 置 2（复用现有 EXPIRED，不新增枚举值）；验证入口先查行是否已失效，锁定后返回"验证码错误次数过多已锁定，请双方重新生成交接码"；重新 generate 产生新 seq 行（attempts 归零）天然解锁（generate 仅双方可调，语义安全）；
- **恒时比较 + 顺序**：码比对改 `hmac.compare_digest`（与邀请码同标准）；调整为先查过期、再比对码，错误信息不区分"码对但过期"；
- **测试正向修正**：新增"失主自报 role=finder 被拒 422（且不计尝试次数、不污染 verified 标记）""连续错 5 次后正确码也锁定 + 重新 generate 天然解锁"两用例；既有迁移链断言（head 0008→0009）随链前移正向修正。

**证据（三项安全验证实跑，独立临时库）**：
```text
① 攻击路径：失主 token + {"code": "<自己屏幕上的码>", "role": "finder"}
   -> HTTP 422 {"code":9001,"message":"角色与身份不符","data":null}
   随后 GET /matches -> match status=1（仍认领中，未被单方打成 COMPLETED）；
   DB 复核：lost_code_verified=false、finder_code_verified=false、attempts=0
② 锁定：同 match 连续 5 次错码（前 4 次 4001"交接码无效"，第 5 次起报锁定），
   第 6 次输入正确码 -> HTTP 400 {"code":4001,"message":"验证码错误次数过多已锁定，
   请双方重新生成交接码"}；DB：该行 status=2(EXPIRED)、attempts=5；
   双方重新 generate 后新 seq 行（attempts=0），正确验证恢复 200
③ 正向回归：失主/拾得者各用正确 role + 对方的码
   -> 200 both_verified=false（单方）→ 200 both_verified=true（双方）
   -> match status=2(COMPLETED)、失物 status=3(已解决)，全链不变
```
- 迁移：`alembic upgrade head` → 0009（PRAGMA 确认 attempts 列存在）→ `downgrade -1`（列删除）→ `upgrade head`（列恢复），三步均 EXIT=0；
- pytest 全量：`396 passed, 2 skipped, 0 failed`，EXIT=0（串行单进程）；py_compile 通过。
