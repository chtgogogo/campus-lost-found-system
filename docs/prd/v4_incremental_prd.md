## 0. 增量基线（v3 已落地事实 + 本次起点）

> 以下为 v3 已上线现状（勘察结论，真实文件佐证），所有 v4 变更**必须基于这些事实**。

- **标签（v3）**：`app/services/tagging_service.py` 抽取 **视觉 label（category.name）+ 颜色词 + 地点词** 三类，**不抽物品名词**（如 钥匙/水杯/书本）。证据：`tagging_service.py:73-87` 仅 add 视觉 label / 颜色 / 地点。
- **匹配公式（v3，Q3 拍板）**：`score = W_PHOTO·photo_sim + W_TAG·tag_jaccard + W_CAT·category_hit + W_TIME·time_decay`，默认 `30/30/25/15`，阈值 `80`。证据：`match_service.py:65-84`、`config` 的 `MATCH_W_PHOTO/W_TAG/W_CAT/W_TIME`、`MATCH_THRESHOLD=80`。
- **模型（v3）**：`FoundItem.keep_status`（0=暂为保管 / 1=未保管）；`contact_allowed`（默认 1）；`LostItem.status`（0待匹配/1匹配中/2待认领/3已解决）；`FoundItem.status`（0待认领/1已解决）。证据：`app/models/item.py:92-94`。
- **IM（v3 需求 D）**：`app/routers/im.py` + `app/services/im_service.py`；会话门控取 `found_item.contact_allowed==1`；`POST /im/sessions` 须传 `match_id` 且当前用户须为会话双方之一。证据：`im.py:86-131`。
- **交接（v3）**：`app/services/handover_service.py` 双动态码交接，作用于「认领中（待交接）」匹配；完成后 `MatchRecord.status=2`、两端物品置已解决。证据：`handover_service.py:48-159`。
- **公示栏（v3）**：`BoardView.vue` 失物/拾物/已完成交接三栏；前端关键词搜索（标题+描述）。证据：`BoardView.vue:14-21,146-172`。

### 0.1 用户报告的缺陷与根因（主理人勘察确认，作为事实）

用户发帖后系统不匹配：失物"银色钥匙"、拾物也写"银色钥匙"，却没匹配上。

**根因 1（标签不抽物品名词）**：`tagging_service` 只抽 颜色/地点/视觉label。纯文字帖"银色钥匙"只抽到 `["银色"]`，"钥匙"丢失——而物品名词恰恰是最关键的区别信号。
**根因 2（公式对纯文字帖永远够不到阈值）**：`photo_sim` 与候选的 `category_hit` 之外，`tag_jaccard` 在纯文字帖（无图→`image_hash` 为 NULL→`photo_sim=0`；视觉 label 缺失→无 noun tag）时即便标签全中也仅 `30+≤15=45 < 80`，**自动匹配永不命中**。

### 0.2 已拍板决策（默认采用，不再追问）

- **决策 1（匹配修复范围）**：同时做两件事——
  - (a) 修自动匹配：补**物品名词抽取** + **重算权重**让"相同文字描述"能自动匹配（见 §3 P0-M、§5 Q2）。
  - (b) 加**用户描述的手动匹配兜底**：能自动的自动，不能的手动。
- **决策 2（未挪动按钮）**：当拾物选「未挪动」(`keep_status=1`) 且拾得者允许联系(`contact_allowed=1`) 时，失主在卡片上**两个按钮都显示**：「与拾取者联系」（可问位置线索）+「申请匹配」（启动自取流程）。

## 1. 产品目标与范围边界

### 1.1 产品目标（一句话）
> **v4 通过「补物品名词标签 + 重算标签驱动匹配公式」根治纯文字描述匹配失效，并补「搜索拾物栏 + 手动匹配兜底 + 未挪动自取」闭环，让“没自动匹配上的失物”也能被找到、被认领。**

### 1.2 本期范围边界

**做（Scope In）**
- M. 修复自动匹配：物品名词成为 tag；匹配改为**标签驱动**，颜色用于共享名词时消歧；重算权重使相同文字描述可自动命中。
- N. 手动匹配兜底：失主在「拾物栏」按关键词搜索、浏览候选，按 `contact_allowed` 分两支（联系 / 申请匹配）。
- K. `keep_status` 改造：模型值 1 文案由"未保管/待领取"改为「未挪动」（枚举不变）；`keep_status=0` 强制 `contact_allowed=1` 且勾选框锁定；`keep_status=1` 不走双码，走自取流程。
- S. 未挪动自取完成：失主「申请匹配」→ 自行寻找 →「完成匹配」→ 单边归档「已完成」（无需拾得者操作）。

**不做（Scope Out）**
- 不改动 v3 已交付基线（标签/感知哈希/IM/分栏/双码交接逻辑主体）。
- 不新建消息表、不引入新前端框架、不新建核心闭环以外的服务。
- 自动匹配阈值流程保留：命中阈值的仍进"我的匹配"栏，手动路径仅兜底。

## 2. 用户故事（角色 / 场景 / 价值）

> 格式：`As a [角色], I want [功能] so that [价值]`。

### A. 失主搜索拾物栏并联系（手动兜底·联系分支）
- **失主**：As a 失主，我希望系统没自动匹配上时，我能在「拾物栏」按关键词搜到候选，so that 我不用干等、能主动找。
- **失主**：As a 失主，我希望对 `contact_allowed=1` 的候选卡片点「与拾取者联系」直接开聊，so that 我能问位置等线索（复用现有 IM）。

### B. 失主申请匹配并自取完成（手动兜底·自取分支 + 未挪动自取）
- **失主**：As a 失主，我希望对 `contact_allowed=0` 的候选点「申请匹配」就能建立匹配，so that 系统替我关联这条拾物。
- **失主**：As a 失主，我希望「未挪动」的拾物我点「申请匹配」后自己去现场找，找到后点「完成匹配」即可归档，so that 拾得者不必再操作、流程更轻。

### C. 拾得者暂为保管（强制联系 + 双码交接，沿用 v3）
- **拾得者**：As a 拾得者，我希望选「暂为保管」时系统强制开启联系并锁定该开关，so that 失主一定能联系到我、走标准双动态码交接，防冒领。
- **系统**：As a 匹配服务，当 `keep_status=0` 时后端须拒绝 `contact_allowed=0` 的发布请求，so that 门控不被绕过。

### D. 拾得者未挪动（无双码 + 自取，文案改名）
- **拾得者**：As a 拾得者，我希望选「未挪动」时文案是"未挪动"而非"未保管"，so that 失主理解物品还在原地、可自行前往。
- **拾得者**：As a 拾得者，我选「未挪动」且允许联系时，失主卡片同时看到「联系」和「申请匹配」两个按钮，so that 失主既能问线索也能直接自取，我无需介入。

### E. 验收：C 失物"钥匙"匹配 A、B（标签驱动·硬性用例）
- **失主/系统**：As a 失主，当我发"钥匙"（纯文字）应同时看到 A（黑色钥匙）与 B（银色钥匙）两条匹配；当我发"银色钥匙"应只看到 B，so that 物品名词是主信号、颜色只在共享名词时消歧。

### 2.1 验收检查项（Given / When / Then，硬性，写入测试闸门）

**AC1 — C="钥匙" 应同时匹配 A、B**
- **Given** 候选 A=`tags=[钥匙,黑色]` 且含 `image_hash`；候选 B=`tags=[钥匙,银色]` 且含 `image_hash`；失物 C=`tags=[钥匙]`（纯文字、无 `image_hash`、`category_name=钥匙`）。
- **When** 系统对 C 执行自动匹配（发布或候选检索，阈值 80）。
- **Then** 匹配结果集合**必须同时包含 A 与 B**（`score≥80`）；A、B 之间**不得**因颜色不同互相排斥。

**AC2 — C="银色钥匙" 应只匹配 B**
- **Given** 同上 A、B；失物 C=`tags=[银色,钥匙]`（纯文字、无 `image_hash`）。
- **When** 系统对 C 执行自动匹配。
- **Then** 匹配结果**必须包含 B**（名词+颜色全中）且 **不得包含 A**（A 缺"银色"）；B 的排序须高于任何仅共享名词但缺颜色的候选。

> 注：AC1/AC2 均为纯文字失物（`photo_sim=0`），因此公式必须保证"共享名词 + 全中颜色"时 `W_tag·1 + W_cat·1 + W_time·1 ≥ 80`（见 §5 Q2 建议默认）。

## 5. 待确认问题（需架构师 / 工程拍板，附建议默认）

### 5.1 阻塞细化（建议尽快确认）

- **Q1 物品名词典范围**：建议**内置校园失物名词典**（钥匙/钥匙串/水杯/水壶/雨伞/雨衣/书本/笔记本/教材/书包/钱包/手机/校园卡/饭卡/身份证/眼镜/耳机/充电宝/优盘/鼠标/卡套/帽子/围巾/手套…）+ **必注入 `category_name` 为规范名词**；词条与颜色/地点同级做子串匹配、保序去重。是否接受此范围？是否先小词表上线、后续 admin 维护（P2-M1）？
- **Q2 公式重算具体方案（建议默认）**：
  - `tag` 因子由对称 Jaccard 改为**查询命中率（containment）**：`tag_hit = |lost.tags ∩ found.tags| / |lost.tags|`，使"标签更少"的纯文字失物也能满命中"标签更丰富"的候选（这是 AC1 通过的关键）。
  - 权重建议（合计 100）：`W_PHOTO=20, W_TAG=40, W_CAT=25, W_TIME=15`，阈值沿用 **80**。验证：
    - AC1 C=[钥匙] vs A=[钥匙,黑色]/B=[钥匙,银色]：`tag_hit=1` → `0+40+25+15=80 ≥80` ✅ 同时匹配 A、B。
    - AC2 C=[银色,钥匙] vs B=[钥匙,银色]：`tag_hit=1` → 80 ✅；vs A=[钥匙,黑色]：`tag_hit=0.5` → `20+25+15=60 <80` ✅ 只匹配 B。
  - 说明：photo 权重由 30 降为 20，是为让纯文字帖（`photo_sim=0`）在满命中时仍能达 80；有图场景仍叠加 photo 上限封顶 100。**具体权重/因子实现由架构师在设计中确认，但必须保证 AC1、AC2 通过。**
- **Q3 手动匹配状态枚举值设计（建议默认）**：`MatchRecord.status` 现有 `0待认领/1认领中/2已完成/3已拒绝`。建议**新增 `MANUAL_PENDING=4`（待自取/自行寻找中）** 用于「申请匹配」后至「完成匹配」前的状态；「完成匹配」置 `2(已完成)`。分栏：进行中={0,1,**4**}，已完成={2,3}。是否接受新增值，还是复用 1(认领中)？
- **Q4 申请匹配是否需拾得者通知（建议默认）**：建议**不通知拾得者**。理由：未挪动=物品未被移动，失主自行前往自取，拾得者无需介入（与"单边确认"一致）。是否接受？若需通知，则走 IM 触达。
- **Q5 搜索端点是否复用现有 BoardView 搜索（建议默认）**：建议**复用现有 `GET /found-items` 列表 + 前端关键词过滤**（与 `BoardView.vue` 现状一致，零新增端点，风险最低）；候选浏览可在「拾物栏」基础上加动作按钮，或独立"手动找物"入口。若数据量大，再补 `GET /found-items?keyword=` 服务端过滤（可选）。采用哪种？
- **Q6 纯文字失物的 `category_id` 解析（关键，建议默认）**：`publish_service` 对无图失物 `first_bytes=b""` → 视觉降级为 fallback 类目，可能 ≠ 候选真实类目，导致候选检索（按 `category_id` 过滤）漏检，**AC1/AC2 的前提会被破坏**。建议：纯文字失物以 `category_name` **精确回退查 `category.id`** 作为 `category_id`（查不到再走视觉 fallback）。是否接受？不解决则自动匹配对纯文字帖整体失效。
- **Q7 无 match 的 IM 会话入口（建议默认）**：现有 `POST /im/sessions` 强制要求 `match_id` 且校验会话双方。手动兜底「联系」时无 match。建议新增入参 `found_id`（+ 失主侧 `lost_id`）建会话，复用门控 `_contact_gateway_blocked` 与审计镜像；会话 `match_id` 可空。是否接受该扩展，还是为手动联系新建独立会话表？
- **Q8 「完成匹配」端点与权限（建议默认）**：建议新增 `POST /matches/{id}/self-complete`，仅限**失主**且匹配为手动自取态（P1-S2）；直接置双端已解决 + `MatchRecord=2`，**不调用 `handover_service`**。是否接受命名与归属？

### 5.2 风险与缓解

- **R1 名词误抽**：描述含"书"等歧义词 → 缓解：名词典优先级（category_name > 名词典 > 颜色 > 地点）+ 最长匹配优先；词表可维护（P2-M1）。
- **R2 公式回归**：containment 改变既有排序 → 缓解：保留类目/时间因子、阈值可配；AC1/AC2 + 既有测试作为回归闸门（P0-M2）。
- **R3 纯文字类目错配**：见 Q6，必须回退 `category_name` 解析，否则自动匹配整体失效。
- **R4 手动匹配滥用**：失主随意「申请匹配」刷匹配 → 缓解：申请前校验失物状态为进行中、同一对不重复建匹配（`_exists_match` 复用）；自取完成需失主确认。
- **R5 未挪动语义误导**：若文案未改清，失主可能误以为已代管 → 缓解：P0-K1 改名「未挪动」+ P2-K1 差异说明。

**状态机要点（v4）**
- 暂为保管(`keep_status=0`, `contact_allowed=1` 强制)：发布 → 自动匹配(阈值)→认领→确认归还→**双动态码交接**→ 双方已解决。
- 未挪动(`keep_status=1`)：发布 → （自动匹配 或 手动申请匹配）→ 失主自取 → **「完成匹配」单边归档** → 双方已解决（无双码、无拾得者操作）。
- 联系门控：`contact_allowed==0` → 不可开 IM，卡片仅「申请匹配」；`==1` → 可开 IM（未挪动时并列「申请匹配」）。
