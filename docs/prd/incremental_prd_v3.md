## 0. 增量基线（v2 已落地事实，本次在其上改造）

> 以下为 v2 已上线现状，所有 v3 变更**必须基于这些事实**。

- **字段（v2）**：`LostItem` / `FoundItem` 已删 `region_code`；`category_name`（自由文本，必填）已替代固定分类下拉；`category_id` 仅作内部匹配键（可空 FK）。
- **地点（v2）**：仍保留文本地点列 `lost_location`（失物，NOT NULL）/ `found_location`（拾物，可空），匹配 `W3` 基于二者 `difflib` 文本相似度。
- **匹配公式（v2）**：`score = W1·category_hit(40) + W2·time_decay(25) + W3·location_similarity(20) + W4·keyword_jaccard(15)`，阈值 `80`，`τ=3天`。
- **公示栏（v2）**：已有「失物 / 拾物 / 已完成交接」三栏，「已完成交接」为独立集合 + 独立关键词搜索。
- **IM 基建（v1 已建，v2 未动）**：`im_session` / `im_message` 两张表已存在（`match_id` 外键、`sender_role`、`content` 等齐全），但路由 `/im/*` 与 WebSocket 为 P1 未完全接入前端。
- **联系开关（已存在）**：`found_item.contact_allowed`（TINYINT，默认 1，"是否愿接收联系"）已落地。
- **配置（已存在）**：`MATCH_W1~W4`、`MATCH_THRESHOLD`、`TIME_DECAY_TAU_DAYS`、`IM_RETENTION_DAYS` 均在 `config.py`。

## 1. 项目信息

- **Language**：中文
- **Programming Language**：沿用现有栈——前端 `Vue3 + Element Plus + Vite + Axios`；后端 `FastAPI + SQLAlchemy`（非默认 React/MUI，因属既有系统增量改造，禁止另起技术栈）
- **Project Name**：`campus_lost_found_v3`
- **原始需求复述（v3 五条变更）**：
  1. 删除"地点"字段：发布表单移除独立"地点"输入，改由用户在描述里写（如"我在食堂二楼捡到一把雨伞，白色的"）。
  2. 自动打标签：发布时系统从"视觉识别标签 + 描述文本"抽取结构化标签并存储（如视觉"白色雨伞" + 描述"食堂二楼" → `["雨伞","白色","食堂二楼"]`）；后端用中文规则匹配"种子分类词 + 颜色词 + 地点词"实现抽取。
  3. 匹配增强：失主发布失物时，先按**照片相似度**匹配，再从标题/描述抽取关键词（"雨伞""白色"）与拾得栏高匹配项做**关键词交集匹配**，综合排序。
  4. 真实站内通信（"联系对方"）："我的匹配"每条匹配加"联系对方"按钮 → 弹临时对话框 → 双方互发消息（类 QQ/微信）→ 消息持久化（保留一定时长，用于冒领后溯源）；受"是否允许认领者联系我"开关约束。
  5. 新增"我的发布"栏：查看自己发布的所有物品；"我的发布"与"我的匹配"都把"已完成"与"进行中"分开存储/分栏展示。

## 2. 产品目标

- **G1｜信息降噪·地点入描述**：去掉独立地点字段，地点随自然语言进入描述，降低表单负担同时保留地点语义，为自动标签提供原料。
- **G2｜结构化标签·可计算**：发布时由"视觉标签 + 描述"自动抽取结构化标签并落库，把非结构化的"描述"升维为可检索、可匹配的计算维度。
- **G3｜匹配增强·准且快**：以"照片相似度 + 标签（关键词）交集"双路综合排序，替代原 W3 文本地点相似度，提升疑似匹配的召回与精度。
- **G4｜站内可信通信·可溯源**：在"我的匹配"提供临时对话"联系对方"，消息持久化用于冒领溯源，并受联系开关约束，闭环防冒领。
- **G5｜个人中心分栏·状态清晰**：新增"我的发布"，与"我的匹配"共同按"进行中 / 已完成"分栏，让用户对自己的物品与匹配一目了然。

> 五目标互相正交：G1 解决"地点怎么填"，G2 解决"描述怎么算"，G3 解决"怎么匹配更准"，G4 解决"怎么沟通可溯源"，G5 解决"怎么看自己的东西"。

## 3. 用户故事（按角色，标注涉及改动）

### 失主（Loser / Claimer）
- 作为失主，我希望发布失物时**不用单独选地点**，直接把"在食堂二楼丢的"写进描述即可，系统自动识别地点标签。——涉及：发布表单（去地点输入）、`tagging_service`、前端 Publish 页。
- 作为失主，我希望发布后系统**自动帮我提取标签**（雨伞/白色/食堂二楼），不必手动打标。——涉及：后端自动标签、`tags` 字段、前端标签展示。
- 作为失主，我希望在"我的匹配"看到的疑似拾得物**既像我的东西（照片相似）又关键词对得上（雨伞白色）**，排序更靠谱。——涉及：`match_service` 新公式、照片相似度。
- 作为失主，我希望对每条匹配能**直接点"联系对方"和拾得者聊两句**确认细节，且聊天记录留着万一冒领能查证。——涉及：`im_session`/`im_message` 复用、「联系对方」按钮、消息留存。

### 拾得者（Finder）
- 作为拾得者，我希望发布拾物时地点也写在描述里，**表单更简单**，系统照样能抽出地点标签。——涉及：发布表单、标签抽取。
- 作为拾得者，我希望在"我的匹配"里能**主动联系来认领的失主**，但**若我关了"允许联系"别人就点不了我**。——涉及：`contact_allowed` 开关、"联系对方"门控。
- 作为拾得者，我希望"我的发布"里能**一眼看到我捡了哪些、哪些已交接完**。——涉及："我的发布"分栏。

### 管理员（Admin）
- 作为管理员，我希望冒领申诉时能从**留存的内部聊天记录**追溯到双方沟通内容，辅助判定。——涉及：`im_message` 留存 / `audit_log` 镜像。

## 5. UI 草图（文字描述）

### 5.1 发布页（失物 / 拾物双 Tab）
- **失物**：移除独立"地点"输入框；保留「物品分类」文本框（视觉 `label` 预填，可改）；「描述」框下方灰字提示："可在描述中写明地点，例如：我在食堂二楼丢了一把白色雨伞"。
- **拾物**：同理移除地点输入；描述提示："例如：我在食堂二楼捡到一把雨伞，白色的"。
- **提交后反馈**：卡片/Toast 展示"系统已自动提取标签： 雨伞 ／ 白色 ／ 食堂二楼 "（chips 形式），让用户感知自动打标结果。

### 5.2 我的匹配（MatchesView）
- 顶部 Tab：**进行中 ｜ 已完成**（按 `match_record.status`：进行中=0/1，已完成=2，已拒绝=3 不显示或归入其他）。
- 每条匹配卡片：物品缩略图 + 标题 + 匹配分 + `tags` chips + 按钮区 **「联系对方」**。
- 「联系对方」按钮：
  - 正常：可点 → 弹出**临时对话框**（消息气泡，上失主下拾得者，或按 `sender_role` 左右分）；底部输入框 + 发送；类 QQ/微信。
  - 对端 `contact_allowed==0`：按钮**置灰**，hover/点击提示"对方暂未开启联系"。
- 对话框关闭后可从"我的匹配"再次进入，历史消息按时间轴加载（复用 `GET /im/sessions/{id}/messages`）。

### 5.3 我的发布（MyPublishView · 新增页面）
- 顶部 Tab：**进行中 ｜ 已完成**。
- 进行中：失物 + 拾物**混合列表**，每条左侧类型徽标（失物/拾物）、标题、状态、标签 chips、发布时间。
- 已完成：同上，仅含已解决/已交接项（失物 `status=3`、拾物 `status=1`）。
- 点击条目可查看详情（含 `tags` 与描述中的地点信息）。

### 5.4 公示栏 / 物品卡片（增强）
- `ItemCard` 增加 `tags` chips 展示（P2 可做标签筛选）。

## 7. 待确认问题 / 风险

### 7.1 需架构师 / 主理人拍板（阻塞细化）
- **Q1 地点列硬删 vs 保留空列**：建议**硬删** `lost_location`/`found_location` 并写迁移（存量数据并入 `description`）；是否接受？是否还有其他模块依赖这两列（如 admin 导出）需先解耦？

- **Q3 综合排序权重与阈值**：新公式建议 `score = w_photo·photo_sim + w_tag·tag_jaccard + w_cat·category_hit + w_time·time_decay`；`w_*` 与阈值初值？是否沿用阈值 80？`MATCH_W3` 改为照片/标签权重，命名是否重命名？
- **Q4 消息留存与溯源**：`IM_RETENTION_DAYS` 当前默认 7 天物理删除；冒领溯源建议**延长至 ≥30 天**或**镜像消息摘要至 `audit_log`**。采用哪种？留存期满清理是否误删溯源所需数据？
- **Q5 "联系对方"开关语义**：本次是否**仅用 `found_item.contact_allowed`** 作为唯一门控（失主联系拾得者看拾得者开关；拾得者联系失主看失主开关——但失主侧无此字段）？是否需 P1-04 给 `lost_item` 补 `contact_allowed` 以对称？

### 7.2 产品细节确认（非阻塞）
- **Q6 标签抽取范围**：是否覆盖**标题**（不仅是描述）？视觉 label 已含颜色（如"白色雨伞"）时，与描述中"白色"如何统一去重（建议按词归一后 set 去重）？

### 7.3 风险与缓解
- **R1 照片相似度性能**：全表图片比对慢 → 缓解：P1-03 候选集裁剪（类目 + 时间窗）。
- **R2 标签抽取误命中**：地点词与分类词重叠（如"书"）→ 缓解：词表优先级（分类 > 颜色 > 地点）+ 最长匹配优先；P1-01 词表可维护。
- **R3 匹配回归**：替换 W3 可能改变既有匹配结果 → 缓解：P0-05 保留类目/时间因子，阈值可配，既有测试同步更新为验收闸门。
- **R4 通信滥用**：站内消息可用于骚扰 → 缓解：受 `contact_allowed` 门控 + 消息禁链接（沿用 v1 WS 过滤）+ 留存溯源。

## 8. 范围与边界（明确"不做什么"）
- **不新建 `messages` 表**：复用既有 `im_session` / `im_message`。
- **不引入新前端框架**：继续 Vue3 + Element Plus，不切换 React/MUI。
- **不改核心业务模型**（发布→匹配→认领→交接→审计闭环不变），仅扩展标签维度与匹配因子、接入既有 IM 能力、新增个人中心分栏。
- **不改动 v2 已完成的交付**（去校区、自由文本分类、中文时间、已完成交接栏）基线。
