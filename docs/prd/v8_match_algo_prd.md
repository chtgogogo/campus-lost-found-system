## 0. 增量基线（v7 已落地事实 + 本次起点）

> 以下为实地 Read 于 `app/services/match_service.py`、`app/core/config.py`、`app/models/item.py` 的事实，所有 v8 变更**必须基于这些事实**。

### 0.1 当前匹配公式（关联需求 ①–⑤ / Q1–Q11）
- **F-M1（公式与权重）**：`app/core/config.py:74-79` 定义 `score = MATCH_W_PHOTO·photo + MATCH_W_TAG·containment + MATCH_W_CAT·category_hit + MATCH_W_TIME·time_decay`，当前值 **20 / 40 / 25 / 15**，阈值 `MATCH_THRESHOLD=80`，时间衰减 `TIME_DECAY_TAU_DAYS=3`。
- **F-M2（containment 离散）**：`match_service.py:60-73` 的 `tag_containment_factor = |lost.tags ∩ found.tags| / |lost.tags|`。分母为失物标签数，**逐标签 0/1 命中**——只取 `1, 1/2, 1/3…` 等离散值，是"全有/全无"主因之一。
- **F-M3（category_hit 二值）**：`match_service.py:38-41` 精确 1.0 / 父级 0.5，无近类目部分信用。
- **F-M4（photo_sim 已连续）**：`match_service.py:49-52` `photo_sim_factor` = 首图感知哈希 Hamming 相似度 ∈ [0,1]；任一 `image_hash` 缺失降级 0.0。**该因子本身已连续**，问题在无图时 20% 权重永久闲置。
- **F-M5（颜色硬门控）**：`match_service.py:75-86` `color_conflict`——失物与候选**双方都指定颜色且颜色集合不相交 → 强制 score=0**。
- **F-M6（deprecated 兼容）**：`location_hit_factor` / `keyword_jaccard_factor` / `tag_jaccard_factor` 作为 [deprecated] 保留，**不被 score 调用**（v3 已移除地点列）。

### 0.2 数据模型现状（关联需求 ④ / Q3–Q5 / Q9–Q10）
- **F-D1（已有字段）**：`LostItem`/`FoundItem`（`app/models/item.py`）已含 `category_id`/`category_name`、`title`、`description`、`images`(JSON)、`tags`(JSON)、`image_hash`(String16)、`lost_time`/`found_time`、`color`(String30，v3 起存在)。
- **F-D2（缺失字段）**：**无** `appearance` / `features` / `location` 独立结构化字段；地点语义自 v3 起并入 `description`（v3 迁移 0002 删除 `lost_location`/`found_location`）。
- **F-D3（颜色已半结构化）**：`color` 列已存在，且颜色词同时进 `tags`（`COLOR_WORDS`）；v8 的"外观"维度应**复用 `color` 列**而非新建。
- **F-D4（类目体系）**：现有 11 类 `phone/wallet/keys/backpack/suitcase/laptop/campus_card/glasses/notebook/umbrella/bottle`（玩偶 doll 已移除：三源零样本、毛绒难以识别，识别时低置信归"其他"）；**"其他"为新增第 12 类**，由视觉低置信降级占位产出（`vision.py` 不污染 `tags`）。

## 1. 产品目标与范围边界

### 1.1 产品目标（一句话）
> **v8 将匹配度从"全有/全无、恒等于 80"重构为"连续可区分"的加权模型：照片相似度在**有图时**真正参与（保持 20%），标签主导 80% 并细分为类目/外观/特征/时间/地点五个连续维度，同时支持"其他"类的纯标签驱动匹配。**

### 1.2 本期范围边界

**做（Scope In）**
- **① 四维度标签权重方案**：在 80% 标签权重内给出 类目/外观/特征/时间/地点 的具体分配（见 §3 P0-①，权重"待主理人拍板"）。
- **② "其他"类匹配规则**：第 12 类无类目权重，匹配度完全由中文标签对应数量（外观/特征/时间/地点）决定。
- **③ 照片相似度激活**：确认 `image_hash` 在发布时计算并存储（字段已存在），有图时 `photo_sim` 连续驱动 20% 权重，无图/无哈希降级 0（绝不伪造）。
- **④ 新增结构化字段**：发布表单采集 **外观 / 特征 / 地点**，`color` 列并入"外观"；前端展示各维度贡献明细。
- **⑤ 阈值复核**：确认 `MATCH_THRESHOLD` 是否仍 80（见 §3 P0-⑤）。
- 演示模式（mock）同步支持上述变更。

**不做（Scope Out）**
- 不改 `keep_status` / `contact_allowed` / `MatchStatus` 枚举语义（沿用 v5–v7）。
- 不改发布/匹配/交接/IM 主流程；本期**只替换打分函数与字段采集**，召回逻辑（名词召回）仅随新增字段微调。
- 不改视觉识别模型本身（`vision.py`），仅消费其 `category_id/label/confidence` 输出，低置信走"其他"降级。
- 不引入新依赖（权重/阈值仍读 `config.py`）。

## 2. 用户故事（角色 / 场景 / 价值）

- **失主**：As a 失主，我希望系统按"类目/外观/特征/时间/地点"给出**连续**匹配分，并能看到每个维度贡献多少，so that 我能判断哪些候选更靠谱，而非所有候选都显示"80% 疑似匹配"。
- **失主**：As a 失主，我丢了"钥匙·黑色·一共三串·7-2·操场"，so that 即便拾得者记成"钥匙·银色·7-2"（颜色不同），也应因**类目命中+时间近**排在"校园卡·黑色·7-2"（类目不符）之前，且二者分数有区分。
- **拾得者**：As a 拾得者，我希望发布时能补充外观/特征/地点，so that 我的拾得物能凭更细的标签精准匹配到失主，而不只靠类目+时间撞大运。
- **管理员**：As a 管理员，我希望"其他"类（视觉无法归类）物品也能通过标签匹配、并在后台看到各维度贡献明细，so that 我能审核误匹配、理解为何某条被推为高匹配。

## 5. 待确认问题（需主理人 / 用户拍板，附建议默认）

### 5.1 阻塞细化（建议尽快确认）

- **Q1 类目是否计入 80% 标签权重内，还是作为独立硬门控？**
  - **现状**：当前 `category_hit` 独立占 25%（在 100 内）；新需求将标签提权到 80% 并细分。
  - **建议默认**：**类目计入 80% 内（30%）**——类目精确命中拿满 30，不匹配则该维 0（但仍可凭外观/特征/时间/地点得分，不会整条 0）。这样 C(钥匙) 凭类目 30 稳超 B(校园卡) 的外观 20，满足用户举例。
  - **备选**：类目作为**独立硬门控**（类目不符直接封顶，如 ≤某上限），更强约束但可能误杀"其他"类。
  - 请主理人确认：**类目计入 80%（默认 30），还是独立硬门控？**

- **Q2 外观/特征/时间/地点 具体分配是否拍板为 类目30/外观20/特征15/时间10/地点5？**
  - **建议默认**：上述分配（见 P0-① 表）。类目最高因它是最强判别；外观次之（颜色+材质+形状）；特征/时间/地点递减。
  - 请主理人确认：**接受该分配，或调整比例（如地点提到 10%、特征降到 10%）？**

- **Q3 新增字段方案：独立列 vs 复用/扩展 tags？**
  - **方案 A（建议默认）**：新增 `appearance`(JSON)、`features`(JSON)、`location`(String/JSON) 独立列；颜色**复用已有 `color` 列**并入外观；同时**镜像关键值进 `tags`** 供既有名词召回兼容。
    - 利：结构清晰、可查询、可单独展示明细；与 v7 字段范式一致。
    - 弊：需 0005 迁移；需维护 tags 镜像。
  - **方案 B（仅扩展 tags）**：不新增列，把"外观/特征/地点"作为带前缀的 tag（如 `外观:金属`、`特征:三串`、`地点:操场`）写入 `tags`/`description`，匹配时解析。
    - 利：零迁移。
    - 弊：tags 语义混杂、明细展示需解析、难校验。
  - 请主理人确认：**方案 A（默认）还是方案 B？**

- **Q4 外观 vs 特征的字段边界 taxonomy？**
  - **建议默认**：外观 = 颜色(`color`列)+材质+形状（**可观测静态属性**）；特征 = 品牌+数量(如"三串")+特殊标记（**可区分个体的属性**）。
  - 请主理人确认：**该边界是否认可？数量"三串"归特征是否同意？**

- **Q5 "其他"类匹配时，缺失的 30% 类目权重是否重分配？**
  - **方案 A（建议默认）**：类目缺失不计入，"其他"类 `score = 20·photo + 80·tag_match_rate`（tag_match_rate 跨四维度合并），**最高可达 100%**（30% 隐含重分配到标签维度）。
  - **方案 B**：类目计 0，"其他"类最高 = 70(标签满)+20(photo)=90，超 80 仍可命中。
  - 请主理人确认：**方案 A（默认，纯标签驱动可达 100%）还是方案 B？**

- **Q6 MATCH_THRESHOLD 是否维持 80？是否引入二级阈值？**
  - **现状**：阈值 80 沿用多版。
  - **建议默认**：**维持 80** 作为"疑似匹配"门控；引入**二级候选阈值 60**（仅展示不自动推送），提升连续分的可解释性（P2-①）。
  - 请主理人确认：**维持 80（默认），还是下调/上调？是否加 60 候选档？**

- **Q7 photo_sim 映射与无图降级**
  - **现状**：`photo_sim = 1 - hamming/maxbits`（线性，已连续）；无图/无哈希→0。
  - **建议默认**：沿用线性映射；**无图降级 0（20% 权重在有图时才生效）**——靠标签四维度的连续化解决"恒等于 80"问题，而非伪造照片分。
  - 请主理人确认：**无图降级 0 是否可接受（默认）？是否改用高斯映射让相似度更敏感？**

- **Q8 时间维度计算：time_decay 曲线 vs 标签时间匹配？**
  - **现状**：`time_decay = exp(-Δt/τ)`（τ=3天）已连续，原占 15%。
  - **建议默认**：**沿用 `time_decay` 曲线**作为"时间"维度（归一化到 10%），保持连续与近因加权；不改为"同日=满"的离散匹配。
  - 请主理人确认：**时间维用 time_decay 曲线（默认）还是 tag 时间相等匹配？τ=3 天是否维持？**

- **Q9 地点相似度粒度**
  - **建议默认**：结构化 `location` 字段；相似度 = 精确相等满，**同楼栋/同区域给部分分**（如"操场" vs "操场东侧"=0.7），跨校区/远距离=0。
  - 请主理人确认：**地点粒度（楼栋/区域/描述）与相似度算法是否认可？**

- **Q10 历史数据兼容（存量回填/降级）**
  - **现状**：v7 已发布物品无 `appearance/features/location` 结构化字段；地点在 `description`。
  - **建议默认**：0005 迁移对存量 `appearance/features` 置空（该维计 0）、`location` 尝试从 `description` 轻量解析（失败置空）；不破坏既有匹配与 v7 失效/软删逻辑。
  - 请主理人确认：**存量降级方案（默认置空+可选解析）是否可接受？**

- **Q11 颜色硬门控是否保留？**
  - **现状**：`color_conflict` 双方都指定颜色且不相交 → 强制 score=0。
  - **建议默认**：**软化为惩罚**（颜色不相交 → 外观维度降级，而非整条 0），与连续化一致；保留"颜色冲突"标记供展示。
  - 请主理人确认：**保留硬门控（整条 0）还是改为软惩罚（默认）？**

### 5.2 风险与缓解

- **R1 权重调整破坏既有匹配质量**：缓解：权重全读 `config.py`，可灰度；保留 deprecated 方法，旧测试可对照。
- **R2 连续化后仍"撞 80"**：缓解：六维细分 + 软惩罚，使偏科候选自然低于/高于 80；二级阈值展示。
- **R3 新增字段迁移**：缓解：0005 独立迁移、可回滚；存量降级不影响 v7 失效/软删。
- **R4 "其他"类误匹配**：缓解：纯标签命中率 + 明细展示 + 管理员审核（P2-③）。
- **R5 tags 镜像一致性**：缓解：发布时统一写入，匹配读 `tags` 与结构化字段双源校验。
