# 已知技术债与取舍（Known Trade-offs）

> 目的：主动登记当前架构中**已知的、有意接受的**短板——每条写清「现状 / 为什么 / 触发条件 / 修法」。
> 这是工程判断力的展示，不是缺陷隐瞒清单；面试深挖到任何一条，答案都在这里。
> 维护纪律：每轮安检/审查后更新；已修条目移入底部「已清账」并留 CHANGELOG 链接。
> 最后更新：2026-09-24（审查 P0/P1/P2 三批修复后）。

## A. 匹配引擎与评测

### A1. 评测集单一标注者、样本量小【已量化】
- **现状**：主集 40 对（参与调参，F1 78.0%）、控制集 30 条（单维度敏感性，93.6%）、盲集 12 对（冻结未调参，首跑 **57.1%**）。
- **为什么接受**：标注成本高；三集分工已把「乐观偏差」量化（主集−盲集 = 20.9pp）。
- **触发条件**：引擎迭代进入 v17+ 时。
- **修法**：扩盲集至 50 对并引入第二标注者算 κ 一致性；盲集暴露的 4 类误配（同款细节区分 / 米色缺色族 / 长间隔衰减被归一化稀释 / 单只数量罚不足）只能用「新盲集或交叉验证」修复——对同一盲集回调参等于把它变成第二个训练集。

### A2. 归一化放大的边界场景
- **现状**：`k = 100/max(已填权重和, 50)` 让信息少的发布仍有区分度；代价是「只填类目+颜色」类低信息对也可能逼近阈值（γ 中性分已把最坏场景从 86 压到 80，v16）。
- **修法方向**：低信息发布单独降低疑似展示优先级（展示层抑制，不动打分语义）。

### A3. 兼容方法仅为存量测试保留
- **现状**：`match_service` 中 `tag_containment_factor` 等一批 deprecated 方法不被 `score` 调用，仅存量测试引用（卡#6 决策：保留零成本兼容层）。
- **修法**：测试改用新口径后整删；触发条件 = 下一轮测试卫生专项。

## B. 数据层与性能

### B1. 我的匹配列表已 SQL 化，其余列表仍为 ORM 简单分页【部分清账】
- **现状**：`GET /matches`（最重路径）已下推 SQL（300 匹配场景 630→5 条语句、165→18ms，见 `scripts/bench_match_list.py`）；管理端审计导出已分页。
- **仍欠**：管理端 `GET /admin/matches` 每页仍走 `build_match_outs` 重打分（页 ≤100 条，量级可控）；`im_service` 会话列表仍有逐会话富化查询（会话数量级小）。
- **修法**：管理端与 IM 列表照搬批量预取模式即可，均无 schema 变更。

### B2. match_record 缺 (lost_id, found_id) 组合唯一约束
- **现状**：防重靠应用层 check-then-insert；并发发布同一对物品理论上可产生重复候选（`MatchExclusion` 表已有唯一索引，同题已解过一次）。
- **修法**：Alembic 迁移加唯一索引 + 应用层 IntegrityError 兜底；半个迁移的量级。

### B3. SQLite 开发 / MySQL 生产双方言
- **现状**：`BigInteger().with_variant(Integer, "sqlite")` 处理主键；`with_for_update` 在 SQLite 为 no-op（交接码并发防重已在 MySQL 侧生效，CI 已加 MySQL service 实跑建表）。
- **残余风险**：SQLite 语义下并发分支无法本地复现，依赖 MySQL 测试 + 代码走查。

## C. 安全

### C1. `/uploads` 静态目录不经鉴权
- **现状**：图片 URL 直链可访问；缓解 = UUID 文件名 + 敏感图（身份证等）建议用户打码（发布页有提示）。
- **修法方向**：签名 URL 或后端鉴权代理；代价是图片流量全过应用层，取舍未拍板。

### C2. Token 存 localStorage
- **现状**：XSS 下 token 可被读取；缓解 = 全站无富文本渲染（description 纯文本展示）、无第三方脚本。
- **修法方向**：HttpOnly Cookie + CSRF 防护，改造成本中等；简历项目阶段接受并明说。

### C3. 前端 role 门控是"第二重"
- **现状**：管理端导航/路由守卫在前端可被绕过，**真实防线是后端 `require_admin`**（所有 /admin 接口均守卫，有测试）。
- 定位：纵深防御的前端层，非安全边界。

## D. 前端

### D1. Element Plus 样式仍走全局 CSS【有意取舍】
- **现状**：JS 已按需（主 chunk 1249KB→582KB，gzip 406→195KB）；CSS 未拆，因为 ElMessage/ElMessageBox 等 JS-API 组件的样式按需引入有坑，全局 CSS（gzip 后小）换确定性。
- **修法**：unplugin 按需样式 + 手动补 JS-API 组件样式导入，收益约几十 KB gzip。

### D2. 无 E2E 测试
- **现状**：前端有 vitest 单测（请求层）+ type-check + 构建三门禁；无 Playwright 端到端。
- **修法**：核心流（注册→发布→匹配→交接）3 条冒烟用例，Playwright 一晚工作量。

## E. 工程

### E1. requirements.txt 用范围版本而非全量 lock
- **现状**：`>=x,<y` 风格 + CLIP 锁 commit；未提交 pip freeze 的 constraints 文件。
- **修法**：`pip-compile` 生成 constraints.txt，CI 双装校验。

### E2. docs/prd 为历史快照，与 v16 代码存在措辞漂移
- **现状**：v3–v10 的 PRD 保留为设计档案（注明"历史"），不随代码回改；现行口径以 CHANGELOG 与本目录文档为准。
