## 1. RepVGG + Triplet 检索重构

**是什么**
- 用 RepVGG 风格的「重参数化」结构替换/增强当前检索用的视觉骨干：训练时多分支（3×3 / 1×1 / BN），
  推理时融合为单路 3×3 卷积，兼顾训练表达力与推理速度。
- 检索头改用 **Triplet Loss**（anchor-positive-negative）训练深度度量嵌入，替换/补充当前
  基于感知哈希 + 六维规则的外观/特征相似度，提升跨类目细粒度判别（如不同颜色同款书包）。

**为何本次无法作为代码 drop 完成**
- RepVGG 与 Triplet 嵌入均须**从零重训视觉/检索模型**，产出新权重；
  当前 `best.pt` 与 `match_service.py` 的六维打分逻辑是既有契约，热替换会破坏
  `test_qa_bestpt_regression`、`test_match` 等回归。
- Triplet 训练需要**三元组采样策略 + 难例挖掘**与配套数据集，属完整训练工程。

**建议后续工作量**
- 检索模型：约 1~2 周（数据对构造 + Triplet 训练 + 导出嵌入头）。
- RepVGG 重参数化接入：约 3~5 天（训练多分支 + 推理融合推理路径验证）。
- 检索服务接入：约 1 周（新增向量检索接口，与现有六维打分做 A/B 或加权融合）。

**风险**
- 重训引入的新权重需重新跑全套 QA 回归；若嵌入与现有 `match_service` 并存，需设计融合权重，
  存在打分口径漂移风险（需与匹配工程师协同校准 12 类口径）。

## 2. 双通道 Transformer 检索

**是什么**
- 检索改为「双通道」：视觉通道（CNN/ViT 图像编码）+ 文本/属性通道（标题、标签、颜色/材质/形状
  属性），两路经 Transformer 跨模态融合，输出统一相似度。
- 相比当前纯视觉哈希 + 规则，可更好利用**语义属性**（如「黑色 皮质 双肩包」）做跨模态匹配。

**为何本次无法作为代码 drop 完成**
- 需要**跨模态 Transformer 训练**（图文/属性-图像对齐），同样必须重训并产出新模型权重。
- `clip_service.py`（CLIP 跨模态）由另一位工程师负责，双通道架构需与其对齐接口，避免重复建设。
- 训练数据需「图像 + 结构化属性」配对，当前数据集以图像+检测框为主，属性标注需补充。

**建议后续工作量**
- 数据属性标注补充：约 1 周。
- 双通道 Transformer 训练：约 2~3 周（含跨模态对齐与难例挖掘）。
- 与 `clip_service` 接口对齐 + 检索服务重构：约 1~2 周。

**风险**
- 与 CLIP 模块职责边界需明确（避免双份跨模态实现）；模型体积/推理延迟上升，可能需 GPU 推理服务，
  超出当前 CPU 进程内推理架构（vision_service）设计。

## 3. Uni-app 跨平台前端

**是什么**
- 用 Uni-app（Vue 语法）一套代码编译到微信小程序 / H5 / App，替代或补充当前 Web 前端，
  覆盖移动端拾物/认领主流程（扫码、拍照上传、IM 联系、交接码核销）。

**为何本次无法作为代码 drop 完成**
- 这是**新建独立跨平台工程**（独立仓库/构建链、小程序账号、云打包），
  不属于后端 `app/` 代码范畴，无法以「后端模块 drop」形式交付。
- 需前端工程脚手架、组件库、与现有 REST API（`/api/v1`）对接、以及小程序平台资质审核。

**建议后续工作量**
- 工程脚手架 + 路由/状态管理：约 3~5 天。
- 核心页面（发布、检索、详情、IM、交接核销）：约 2~3 周。
- 小程序提审 + 真机联调：约 1 周。

**风险**
- 小程序平台审核不确定性与「失物招领」类目合规要求；需后端补充小程序登录（code2session）
  与现有 JWT 体系打通；IM 轮询（当前 4s 轮询）在移动端需评估升级为 WebSocket/订阅。
