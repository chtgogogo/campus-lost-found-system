## 第一部分：应用启动 - main.py 到底在干什么

### 1.1 应用工厂模式（Application Factory）

```python
# app/main.py 核心结构
def create_app() -> FastAPI:
    app = FastAPI(...)                    # 创建 FastAPI 实例
    app.add_middleware(CORSMiddleware, ...)  # 添加 CORS 中间件
    app.include_router(auth.router, ...)    # 注册路由
    app.mount("/uploads", ...)             # 挂载静态文件
    register_exception_handlers(app)        # 注册异常处理器
    return app

app = create_app()  # 模块级别创建应用实例
```

**为什么用应用工厂？**
1. **测试友好**：可以创建多个独立的应用实例，每个测试用例有自己的数据库
2. **配置灵活**：可以在创建时传入不同的配置（开发/测试/生产）
3. **避免全局状态**：所有配置都在 `create_app` 里完成，没有隐藏的全局初始化

### 1.2 生命周期钩子（lifespan）

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动时执行（只执行一次）
    init_db()                              # 1. 建表
    with SessionLocal() as db:
        seed_categories(db)                 # 2. 写入种子分类
    app.state.vision = get_vision_service() # 3. 预热视觉模型
    yield                                   # 4. 应用运行中...
    # 关闭时执行（可选，释放资源）
```

**关键点**：
- `init_db()`：调用 `Base.metadata.create_all()` 根据 SQLAlchemy 模型自动建表
- `seed_categories()`：首次启动时写入 12 个分类（手机/钱包/钥匙/.../其他）
- `get_vision_service()`：加载 YOLOv8 模型，进程内只加载一次（单例模式）

### 1.3 路由注册的 prefix 机制

```python
app.include_router(auth.router, prefix=settings.API_V1_PREFIX)  # /api/v1
app.include_router(items.router, prefix=settings.API_V1_PREFIX)
```

这意味着：
- `auth.router` 里的 `@router.post("/login")` → 实际路径是 `/api/v1/auth/login`
- `items.router` 里的 `@router.post("/lost")` → 实际路径是 `/api/v1/items/lost`

**设计价值**：将来 API 版本升级时，只需要改 `API_V1_PREFIX = "/api/v2"`，所有路由自动升级。

### 2.2 匹配权重配置（面试必问）

```python
# v10 七维权重（合计 100）
MATCH_W2_PHOTO_CAT: float = 20.0   # 照片/系统分类一致性
MATCH_W2_QTY: float = 15.0         # 量词一致性
MATCH_W2_COLOR: float = 20.0       # 颜色一致性
MATCH_W2_STATE: float = 10.0       # 状态/形容词
MATCH_W2_PLACE: float = 15.0       # 地点四级命中
MATCH_W2_KEYWORD: float = 10.0     # 其他关键词
MATCH_W2_TIME: float = 10.0        # 时间衰减
```

**为什么权重是这些数字？**
- 类目/颜色权重最高（20）：类别错了基本不可能是同一件
- 量词/地点次之（15）：数量和地点是重要佐证
- 状态/关键词/时间最低（10）：噪声较大，权重次之

**面试回答模板**：
> "权重是和导师商定的，写在配置里可复现可调。类目权重最高是因为类别错了基本不可能是同一件，这是最强判别信号。"

### 2.3 归一化参数（防误报）

```python
MATCH_NORMALIZE: bool = True          # 归一化开关
MATCH_NORM_MIN_WEIGHT: float = 50.0   # 防爆下限
MATCH_THRESHOLD: float = 80.0         # 疑似匹配阈值
```

**归一化公式**：
```
k = 100 / max(W_provided, MATCH_NORM_MIN_WEIGHT)
total = clamp(raw_total * k, 0, 100)
```

**为什么要归一化？**
假设失主只填了类目（没写任何文字），那么：
- W_provided = 20（只有 photo_category 维度提供了信息）
- k = 100 / max(20, 50) = 2.0
- 如果 raw_total = 20（只有类目命中），total = 20 * 2.0 = 40 分

**如果没有防爆下限**：
- k = 100 / 20 = 5.0
- total = 20 * 5.0 = 100 分（满分！但信息很少）

所以 `MATCH_NORM_MIN_WEIGHT=50.0` 是为了防止信息不完整的用户得到不合理高分。

## 第三部分：匹配引擎 - match_service.py 逐行解析

### 3.1 特征抽取流水线（extract_features）

```python
def extract_features(self, item, is_lost: bool) -> ItemFeatures:
    # 1. 拼装原始文本
    text = self._raw_text(item, is_lost)
    
    # 2. 按顺序抽取（每步扣除已命中片段，防止重复计分）
    place, rest = extract_place(text)           # 先抽地点
    colors, rest = extract_color_words(rest)    # 再抽颜色
    qty, rest = extract_qty(rest)               # 再抽数量
    states, rest = extract_states(rest, ...)    # 再抽状态
    
    # 3. 残余文本提取关键词
    keywords = self._residual_keywords(rest, category_name)
    
    return ItemFeatures(...)
```

**为什么要按顺序抽取？**
假设文本是"图书馆三楼的黑色钥匙"：
1. `extract_place` → 地点="图书馆三楼"，rest="的黑色钥匙"
2. `extract_color_words` → 颜色="黑色"，rest="的钥匙"
3. `extract_qty` → 数量=无，rest="的钥匙"
4. `extract_states` → 状态=无，rest="的钥匙"
5. `residual_tokens` → 关键词={"钥匙"}

**如果不按顺序**，"黑色"可能被当作关键词而不是颜色。

### 3.2 ItemFeatures 数据结构

```python
@dataclass
class ItemFeatures:
    category_id: Optional[int] = None
    category_name: str = ""
    qty: set[tuple[int, str]] = field(default_factory=set)      # {(1, "串"), (2, "个")}
    colors: set[str] = field(default_factory=set)                # {"黑色", "银色"}
    states: set[str] = field(default_factory=set)                # {"全新", "九成新"}
    place: dict[str, set[str]] = field(default_factory=dict)     # {"building": {"图书馆"}, "floor": {"三楼"}}
    keywords: set[str] = field(default_factory=set)              # {"iPhone", "14"}
    residual_text: str = ""                                       # 原始文本（调试用）
```

**为什么用 set 而不是 list？**
- 集合天然去重（用户写"黑色 黑色"只保留一个）
- 集合支持 O(1) 的 `in` 操作（判断某个 token 是否命中）
- 集合支持交集/并集操作（计算命中率）

### 3.3 七维打分详解

#### 3.3.1 photo_category（照片/类目一致性）

```python
@staticmethod
def _score_photo_category(lost_f: ItemFeatures, found_f: ItemFeatures, exact_category: bool) -> float:
    # 1. 任一侧缺失类目 → 中性 10 分
    if not lost_f.has_category or not found_f.has_category:
        return PHOTO_CAT_NEUTRAL  # 10
    
    # 2. 双方都是"其他"类 → 中性 10 分（类目无判别力）
    if lost_f.category_name == "其他" and found_f.category_name == "其他":
        return PHOTO_CAT_NEUTRAL  # 10
    
    # 3. 精确同类目 → 20 分
    same = lost_f.category_id == found_f.category_id
    if same:
        return PHOTO_CAT_SAME if exact_category else PHOTO_CAT_APPROX  # 20 or 10
    
    # 4. 父子级/近似 → 10 分（如"证件" vs "学生证件"）
    if lost_f.category_name in found_f.category_name or ...:
        return PHOTO_CAT_APPROX  # 10
    
    # 5. 完全不同 → 0 分
    return PHOTO_CAT_DIFF  # 0
```

**设计价值**：
- 双方都是"其他"时给中性分（10），而不是 0 分，因为"其他"类无判别力
- 支持父子级近似（"证件" vs "学生证件"），提高召回率

#### 3.3.2 qty（量词一致性）

```python
# scoring_refs.py 中的档位定义
def qty_score(lost_qty, found_qty) -> float:
    # 五档分值：完全相同 15 / 单双匹配 12 / 模糊匹配 10 / 有数量信息 7 / 无信息 0
    
    if lost_qty == found_qty:           # 完全相同
        return 15.0
    if is_single_double_match(lost_qty, found_qty):  # 单双匹配（一个 vs 一对）
        return 12.0
    if has_partial_match(lost_qty, found_qty):       # 模糊匹配（如"多个" vs "两个"）
        return 10.0
    if lost_qty or found_qty:            # 一方有数量信息
        return 7.0
    return 0.0
```

**为什么是五档而不是二值（匹配/不匹配）？**
因为"一个"和"一对"不完全相同，但有很强的关联性。五档设计更精细。

#### 3.3.3 color（颜色一致性）+ 软化机制

```python
# color_family.py
def color_score(lost_colors, found_colors) -> tuple[float, bool]:
    """
    Returns:
        (score, color_conflict): score 是 0-20 分，color_conflict 是是否冲突
    """
    if not lost_colors or not found_colors:
        return 0.0, False  # 一方无颜色信息
    
    # 颜色家族归一化（深蓝 → 蓝色系）
    lost_families = {get_color_family(c) for c in lost_colors}
    found_families = {get_color_family(c) for c in found_colors}
    
    if lost_families & found_families:  # 有交集
        return 20.0, False
    
    # 冲突：双方都指定了颜色但不一致
    # 软化：只让 color 维度计 0，不连坐其他维度
    return 0.0, True  # color_conflict=True
```

**软化机制（v8 改进）**：
- 旧版：颜色冲突 → 整条判 0（太粗暴）
- 新版：颜色冲突 → 只在 color 维度计 0，material/shape 照常参与

**面试回答**：
> "旧版颜色不一样就直接否掉，太粗暴。新版改成'软化'，颜色只在外观维度计 0，材质/形状照常参与，更合理。"

#### 3.3.4 time（时间衰减）

```python
# utils/time_decay.py
def time_decay(delta_days: float, tau: float = 15.0) -> float:
    """指数衰减：time = exp(-Δd/τ)"""
    import math
    return math.exp(-delta_days / tau)

# match_service.py
def _score_time(lost, found) -> tuple[float, bool]:
    # 1. 失物侧时间缺失 → 0 分，不进分母
    if lost_time is None:
        return 0.0, False
    
    # 2. 拾物侧时间缺失 → 中性分，进分母
    if found_time is None:
        return TIME_SCORE_NEUTRAL, True  # 5.0, True
    
    # 3. 双方都有 → 指数衰减
    decay = time_decay(delta_days(lost_time, found_time), settings.MATCH_TIME_TAU_DAYS)
    return settings.MATCH_W2_TIME * decay, True  # 10 * decay
```

**为什么 τ=15 天？**
- 校园失物招领场景：大多数失物在 1-3 天内找回
- τ=15 天意味着：1 天内找回 ≈ 93 分，3 天内找回 ≈ 82 分，7 天内找回 ≈ 63 分
- 超过 30 天基本不匹配了

### 3.4 归一化计算（面试重点）

```python
def _normalize_factor(provided_weight: float) -> float:
    """
    k = 100 / max(W_provided, MATCH_NORM_MIN_WEIGHT)
    
    铁律：W_provided 只由失主侧决定（候选侧永不进分母）
    """
    if not settings.MATCH_NORMALIZE:
        return 1.0  # kill switch
    if provided_weight <= 0:
        return 1.0
    return 100.0 / max(provided_weight, float(settings.MATCH_NORM_MIN_WEIGHT))

def _provided_weight(provided: dict[str, bool]) -> float:
    """W_provided = Σ(该维度 provided ? 该维度满分 : 0)"""
    maxima = dim_max_scores()  # {"photo_category": 20.0, "qty": 15.0, ...}
    return sum(maxima[d] for d in V2_DIMENSIONS if provided.get(d))
```

**具体例子**：

失主填写了：类目（手机）、颜色（黑色）、地点（图书馆）
- provided = {"photo_category": True, "qty": False, "color": True, "state": False, "place": True, "keyword": False, "time": False}
- W_provided = 20 + 20 + 15 = 55
- k = 100 / max(55, 50) = 1.818

假设 raw_total = 45（各方面都不错），total = 45 * 1.818 = 81.81 分 → 达到阈值 80，判定为疑似匹配。

## 第四部分：视觉识别 - vision_service.py 的降级铁律

### 4.1 永不抛异常的设计

```python
def predict(self, image_bytes: bytes) -> dict:
    """永不抛异常；无模型/无检测→降级为有效活跃分类+confidence=0.0"""
    
    # 1. 双模型皆不可用 → 降级
    if self._coco_model is None and self._world_model is None:
        return self._fallback()
    
    # 2. 图片解码失败 → 降级
    try:
        img = self._decode_image(image_bytes)
    except Exception:
        return self._fallback()
    
    # 3. 推理失败 → 降级
    try:
        results = self._coco_model.predict(...)
    except Exception:
        return self._fallback()
    
    # 4. 无检测结果 → 降级
    if best is None:
        return self._fallback()
    
    return {"category_id": best[0], "label": best[1], "confidence": best[2]}

def _fallback(self) -> dict:
    """降级：返回「其他」类 + confidence=0.0"""
    cat = next((c for c in self._active if c[1] == "其他"), None)
    return {"category_id": cat[0], "label": "其他", "confidence": 0.0}
```

**设计价值**：
- 无论发生什么（无 GPU、无权重、图片损坏、推理异常），发布流程都不会中断
- 用户看到的是"类目显示为'其他'"，而不是系统崩溃
- 这就是"降级铁律"：服务可用性 > 识别准确性

### 4.2 进程内单例模式

```python
_vision_instance: Optional[VisionService] = None

def get_vision_service() -> VisionService:
    """获取（惰性创建）进程内视觉服务单例。"""
    global _vision_instance
    if _vision_instance is None:
        _vision_instance = VisionService()  # 只创建一次
    return _vision_instance
```

**为什么用单例？**
- YOLOv8 模型加载很慢（几秒到几十秒）
- 进程内只加载一次，所有请求共享同一个模型实例
- 避免每次请求都重新加载模型

### 5.1 发布失物的完整流程

```python
def publish_lost(self, publisher, dto, ip=None, ua=None):

    image_urls = storage_util.save_images(dto.images)

    category_id = self._resolve_category_id(dto.category_name.strip(), vision_result, tags)
    
    # 5. 计算感知哈希
    image_hash = PerceptualHash.compute(first_bytes) or None
    
    # 6. 入库
    lost = LostItem(
        publisher_id=publisher.id,
        category_id=category_id,
        category_name=category_name,
        title=dto.title,
        description=dto.description,
        images=image_urls,
        tags=tags,
        image_hash=image_hash,
        appearance=dto.appearance,
        features=dto.features,
        location=dto.location,
        lost_time=dto.lost_time,
        status=0,  # 待匹配
    )
    self.db.add(lost)
    self.db.flush()
    
    # 7. 写审计日志
    audit_service.write_audit(self.db, user_id=publisher.id, action="publish_lost", ...)

```

### 5.2 类目解析优先级（v4 改进）

```python
def _resolve_category_id(self, category_name, vision_result, noun_tags):
    """v4：名词优先于视觉降级"""
    
    # 优先级1：用户填写的类目名精确命中
    if category_name:
        cat = db.query(Category).filter(Category.name == category_name).first()
        if cat:
            return cat.id
    
    # 优先级2：名词 tag 命中种子类目
    for noun in noun_tags:
        cat = db.query(Category).filter(Category.name == noun).first()
        if cat:
            return cat.id
    
    # 优先级3：回退视觉结果
    return self._category_from_vision(vision_result)
```

**设计价值**：
- 名词 tag 的准确率通常高于视觉识别（用户知道自己丢了什么）
- 视觉识别只是辅助，不能完全依赖
- 优先级：用户填写 > 名词提取 > 视觉识别

### 5.3 反向主动匹配（核心亮点）

```python
def _reverse_match_lost(self, lost: LostItem) -> list[MatchRecord]:
    """发布失物时反向匹配候选拾物"""
    
    # 1. 候选召回：只召回「同类目 ∪ 共享物品名词」的拾物
    candidates = self._recall_lost_candidates(lost)
    
    # 2. 对每个候选打分
    scored: list[tuple[float, FoundItem]] = []
    for f in candidates:
        if self._exists_match(lost.id, f.id):  # 幂等去重
            continue
        scored.append((self._matcher.score(lost, f), f))
    
    # 3. 按分数降序排序
    scored.sort(key=lambda pair: (-pair[0], pair[1].id))
    
    # 4. 保底前 N 条 + 所有疑似（v10 变更 B）
    created: list[MatchRecord] = []
    for score, f in _cut_with_suspects(scored, settings.MATCH_TOP_N):
        m = MatchRecord(
            lost_id=lost.id,
            found_id=f.id,
            match_score=score,
            status=0,  # 待认领
        )
        self.db.add(m)
        created.append(m)
    
    if created:
        lost.status = 1  # 匹配中
    
    return created
```

### 5.4 候选召回的性能优化

```python
def _recall_lost_candidates(self, lost: LostItem) -> list[FoundItem]:
    """只召回「同类目 ∪ 共享物品名词」的拾物，避免全库暴力比对"""
    
    # 1. 提取失物的物品名词标签
    noun_tags = {t for t in (lost.tags or []) if t in NOUN_SET}
    
    # 2. 查询所有待认领的拾物
    candidates = db.query(FoundItem).filter(
        FoundItem.status == 0,  # 待认领
        FoundItem.deleted_at.is_(None),  # 未删除
    ).all()
    
    # 3. 过滤：同类目 或 共享物品名词
    def _recalled(f: FoundItem) -> bool:
        if f.category_id == lost.category_id:  # 同类目
            return True
        if not noun_tags:
            return False
        return bool(noun_tags & set(f.tags or []))  # 共享物品名词
    
    return [f for f in candidates if _recalled(f)]
```

**性能关键**：
- 不是拿失物去和全库每件拾物算分（太慢）
- 先通过类目或物品名词过滤，只对少量候选算分
- 时间复杂度从 O(N) 降到 O(k)，k << N

```python
    category_id: Mapped[int | None] = mapped_column(ForeignKey("category.id", ondelete="RESTRICT"))
    category_name: Mapped[str] = mapped_column(String(100))  # 冗余存类目名，便于展示
    title: Mapped[str] = mapped_column(String(100))
    description: Mapped[str] = mapped_column(Text)
    images: Mapped[list | None] = mapped_column(JSON)         # 图片 URL 数组
    color: Mapped[str | None] = mapped_column(String(30))
    tags: Mapped[list | None] = mapped_column(JSON)           # 结构化标签
    image_hash: Mapped[str | None] = mapped_column(String(16))  # 感知哈希
    appearance: Mapped[str | None] = mapped_column(String(255))  # 外观描述
    features: Mapped[str | None] = mapped_column(String(255))    # 特征描述
    location: Mapped[str | None] = mapped_column(String(128))    # 地点描述
    lost_time: Mapped[datetime | None] = mapped_column(DateTime)
    status: Mapped[int] = mapped_column(SmallInteger, default=0)  # 0待匹配/1匹配中/2待认领/3已解决
    created_at: Mapped[datetime] = mapped_column(DateTime, default=utcnow)
    expires_at: Mapped[datetime | None] = mapped_column(DateTime, default=utcnow+90天)
    deleted_at: Mapped[datetime | None] = mapped_column(DateTime)  # 软删除
```

### 6.2 为什么用 BigInteger + with_variant？

```python
id: Mapped[int] = mapped_column(BigInteger().with_variant(Integer, "sqlite"))
```

**设计价值**：
- SQLite 不支持 BigInteger，`with_variant` 会自动降级为 Integer
- MySQL 用 BigInteger（支持更大数字，更安全）
- 业务代码零改动，ORM 自动处理差异

### 6.3 软删除 vs 物理删除

```python
deleted_at: Mapped[datetime | None] = mapped_column(DateTime)
```

**软删除的好处**：
1. **审计留痕**：删除的记录还在库里，配合审计表可追溯"谁什么时候删了什么"
2. **可恢复**：理论上清掉 `deleted_at` 即可恢复
3. **查询过滤**：所有查询都带 `deleted_at.is_(None)` 过滤，已删数据对普通业务不可见

```python
# 查询时过滤已删除
db.query(LostItem).filter(LostItem.deleted_at.is_(None)).all()
```

## 第八部分：防冒领设计 - 双码交接

### 8.1 为什么不用单码？

传统做法：失主生成一个码，拾主输入这个码完成交接。

**问题**：码可能被截获（截图、偷看），第三方可以冒领。

### 8.2 双码交叉验证

```python
# handover_service.py
def generate_code(self, match_id: int, user_role: str) -> HandoverCode:
    """生成 6 位动态码，30 分钟有效"""
    code = ''.join(random.choices('ABCDEFGHJKLMNPQRSTUVWXYZ23456789', k=6))
    # 注意：避开了 0/O/1/I 等易混字符
    
    return HandoverCode(
        match_id=match_id,
        code=code,
        qr_token=generate_qr_token(),
        verified_by_lost=False,
        verified_by_finder=False,
        expire_at=datetime.now() + timedelta(minutes=30),
    )

def verify(self, match_id: int, user_role: str, code: str, gps: dict) -> bool:
    """验证交接码"""
    handover = db.query(HandoverCode).filter(
        HandoverCode.match_id == match_id,
        HandoverCode.expire_at > datetime.now(),  # 未过期
    ).first()
    
    if not handover:
        raise HandoverInvalidError("交接码无效或已过期")
    
    # 双方都必须验证通过
    if user_role == "lost":
        if code != handover.code:
            raise HandoverInvalidError("交接码错误")
        handover.verified_by_lost = True
    elif user_role == "finder":
        if code != handover.code:
            raise HandoverInvalidError("交接码错误")
        handover.verified_by_finder = True
    
    # 双方都验证通过 + GPS 一致 → 交接完成
    if handover.verified_by_lost and handover.verified_by_finder:
        if verify_gps(gps, ...):
            complete_handover(match_id)
            return True
    
    return False
```

**面试回答**：
> "失主和拾主各生成一个码，双方必须输入对方的码才能完成交接。这样即使码被截获，第三方也无法完成交接（因为不知道另一方的码）。"
